Executive Summary

Selected project: distributed parsing, feature construction, and anomaly/alert characterization over the Thunderbird supercomputer system log — a real, peer-reviewed, openly licensed dataset of raw console/syslog output from Sandia National Laboratories' 9,024-processor Thunderbird supercomputer. The dataset comprises 211,212,192 log lines spanning 244 days, at a documented raw size of 29.60 GB, with per-line alert/non-alert labels already present [He, Zhu, He, Lyu — Loghub, arXiv 2020 / ISSRE 2023], [Loghub GitHub, logpai]. This is the dataset's true documented size — it is not a subset, sample, or artificial scale-up, and it falls inside the 10–40 GB range on its own.

The data is genuinely unstructured: each line is free-form console/syslog text produced by heterogeneous kernel, daemon, and hardware-monitoring subsystems, with no fixed schema across message types. Extracting any structured signal (per-node error rates, alert timelines, event-template frequency) requires distributed log parsing across 211 million lines — a canonical Big Data problem, not an ordinary query. Every rubric technology has a non-artificial role: HDFS stores the raw log partitioned by time window; PySpark performs distributed template mining/parsing (Drain-style), per-node and per-window feature aggregation, and sequence construction; MongoDB stores parsed log-event documents whose parameter fields genuinely vary by template — a real semi-structured storage need, not a bolt-on; Streamlit renders an interactive alert-timeline and template-frequency dashboard; Docker containerizes the dashboard and database for reproducible grading.

Domain fit: this is squarely a low-level systems / HPC telemetry project (preferred domain #2). The dataset is one of the three most-used benchmarks in the log-anomaly-detection literature [Juknys, 2023 literature review], with an unbroken, citable research lineage from 2007 (the original supercomputer-log study that produced this data) through active 2023–2024 work, leaving clear room for a student-scale, fully open, reproducible distributed pipeline. Estimated effort: 7–10 focused days; no GPU or paid software required.

1. Title

"Distributed Template Mining and Alert-Pattern Characterization in Supercomputer Console Logs Using PySpark, HDFS and MongoDB"

Names the domain (HPC/supercomputer system logs), the Big Data mechanism (distributed template mining across a 211-million-line corpus), and the concrete stack, without overstating scientific novelty.

2. Problem Statement

Sandia National Laboratories' Thunderbird supercomputer (9,024 processors, 27,072 GB memory) produced a continuous console/syslog stream over 244 days, released as a labelled research dataset of 211,212,192 log lines (29.60 GB raw text) [Loghub]. Each line is free-form text emitted by whichever kernel module, daemon, or hardware-monitoring subsystem generated it, with no consistent column structure across message types; a small subset of lines are pre-labelled as alerts (hardware/software fault indications) rather than routine status output.

The analytical problem is to recover structure from this unstructured stream at scale: mine the finite set of underlying log "templates" (recurring message shapes with variable parameters — node IDs, addresses, timestamps, counters), classify each of the 211 million lines against that template set, and use the resulting structured event stream to characterize alert timing, per-node fault concentration, and template-frequency drift over the 244-day window. This is not achievable through ordinary database querying because the raw data is not yet in queryable form — parsing free text into structured events at 211-million-line scale is itself the distributed computation, and only after that step does any SQL-like query become meaningful.

Who benefits: HPC system operators and reliability researchers, mirroring the original purpose of this data family — early detection of developing hardware/software faults in large compute clusters, as established by the foundational study that first analyzed logs of this kind [Oliner & Stearley, DSN 2007].

Why not single-machine: line-by-line regex/template matching across 211 million records, followed by per-node time-windowed aggregation and sequence construction (sliding windows of recent event types per node, the standard input representation for log-based anomaly detection [Du et al., DeepLog, CCS 2017]), are naturally expressed as partitionable, order-sensitive distributed transformations. A single Python process parsing this file line-by-line would need to hold intermediate template-frequency state for the entire run and cannot exploit multi-core/multi-node parallelism without re-implementing what Spark already provides.

3. Extended Problem Statement

Volume

29.60 GB raw text, 211.2 million lines (Thunderbird alone); optionally +4.7 million lines / 708.76 MB (BGL) for a two-system comparison, ~30.3 GB combined.

Variety

Genuine and severe: dozens of distinct message-generating subsystems (kernel, PBS scheduler, hardware monitors, network stack) each with their own line format; no shared schema across message types until parsing recovers one. This is the concrete justification for storing parsed events as MongoDB documents rather than a single rigid table.

Velocity

Not a live streaming problem for this project — the log is a historical, already-collected batch archive. We treat this honestly as a batch Big Data problem; we do not manufacture a streaming/velocity narrative that the data does not support.

Data quality & schema complexity

Free-text messages contain embedded variable tokens (hex addresses, PIDs, timestamps, counters) that must be masked/extracted for template mining to converge; alert labels are sparse relative to routine (non-alert) lines, giving a rare-event/imbalanced characteristic similar to other fault/failure-detection problems.

Distributed processing requirements

Line-level tokenization and template-matching at 211M-row scale; per-node groupBy for time-windowed event-count features; ordered sliding-window sequence construction per node (a shuffle-heavy operation), all of which are the actual justification for PySpark's partitioned execution model.

Query & analytical requirements

Filter by date range, node ID, template/event type, alert-only view; drill into a specific node's event timeline — the MongoDB + Streamlit query surface, built on Spark-produced aggregates rather than re-scanning the raw log per interaction.

Scalability bottlenecks to discuss in the report

Shuffle cost of the per-node ordered-window operation; skew if a small number of nodes dominate log volume; small-file vs. large-file trade-off when choosing the HDFS block/partition granularity for a single 29.6 GB text file.

Example Spark operations

from pyspark.sql import functions as F, Window
import re

raw = spark.read.text("hdfs:///raw/thunderbird/*")

# Tokenize: label, timestamp, node, message (Thunderbird line format)
parsed = raw.select(
    F.regexp_extract("value", r"^(\S+)", 1).alias("label"),
    F.regexp_extract("value", r"^\S+\s+(\d+)", 1).alias("epoch"),
    F.regexp_extract("value", r"(tbird-\S+)", 1).alias("node_id"),
    F.regexp_extract("value", r"^\S+\s+\S+\s+\S+\s+\S+\s+\S+\s+\S+\s+(.*)$", 1).alias("message")
)

# Mask variable tokens to approximate a Drain-style template signature
masked = parsed.withColumn(
    "template_sig",
    F.regexp_replace(F.regexp_replace("message", r"\d+", "<*>"), r"0x[0-9a-fA-F]+", "<*>")
)

templates = masked.groupBy("template_sig").agg(F.count("*").alias("occurrence_count"))

# Per-node weekly window features for anomaly-detection-style modelling
w = Window.partitionBy("node_id").orderBy("epoch").rowsBetween(-49, 0)
seq = masked.withColumn("recent_templates", F.collect_list("template_sig").over(w))

Potential statistical / ML methods

Primary deliverable is descriptive analytics (template frequency, alert timelines, per-node fault concentration). As a stretch goal, a sequence-window classifier (Logistic Regression on template-count vectors, or an LSTM as in DeepLog) predicting whether a window contains an alert can be trained. This is explicitly optional — see MVP.

Performance / scalability considerations to document

Regex-parsing throughput vs. partition count; shuffle volume for the per-node ordered-window operation; effect of HDFS block size on a single large text file's parallelism; template-count skew if a handful of templates dominate the corpus.

Storage sizing rationale

Raw log (~29.6–30.3 GB) + HDFS replication (default factor 3, reducible to 1 in pseudo-distributed mode) + Parquet processed output (typically smaller than raw text due to columnar compression, but template/parameter expansion can offset some of that) + MongoDB data files. 150 GB free SSD is comfortable; ~90 GB is the tight floor with replication factor 1.

Single-machine pseudo-cluster adaptation

Run Hadoop in pseudo-distributed mode (single-node HDFS, dfs.replication=1) and Spark in local mode (local[*]). This is the standard, examiner-recognized way to demonstrate genuine HDFS block storage and Spark partitioned/DAG execution without a physical multi-node cluster.

Risks and Mitigations

RiskMitigation
Download/extraction of a 29.6 GB archive is slow or interruptedUse resumable download (curl -C -); start acquisition on Day 1; verify with provided checksums if available.
HDFS configuration problems on first setupUse pseudo-distributed single-node mode with replication factor 1; follow the official Hadoop single-node guide exactly; keep a Docker-based Hadoop image as a fallback.
Spark memory pressure / OOM on 32 GB RAM during full-corpus parsingTune spark.executor.memory/spark.driver.memory conservatively; process in time-window chunks rather than the whole 211M lines at once during development; prototype logic on a 1 GB slice first.
Naive template-masking over- or under-merges distinct message typesManually inspect a sample of ~50 mined templates against raw lines to sanity-check; adjust masking regex granularity (e.g., separate hex vs. decimal tokens) if merging looks wrong; document known limitations honestly in the report.
Long preprocessing times eating into the one-week schedulePrototype the Spark job on a small slice first (fast iteration), then scale to the full 29.6 GB only once correct; cache intermediate DataFrames where reused.
NoSQL schema issues (inconsistent parameter fields breaking queries)Store extracted parameters inside a nested subdocument (parameters: {...}) rather than flattening to top-level fields, so differing field sets never break document structure.
Docker networking failures between app and MongoDB containersUse Docker Compose (not standalone `docker run`) so service-name DNS resolution works automatically.
Severe class imbalance in alert labels weakens the optional classifierReport F1/MCC/recall rather than accuracy; treat the classifier as a clearly-labelled optional stretch goal, not a core deliverable.
Streamlit UI performance with large aggregate tablesNever query raw HDFS/Parquet directly from Streamlit; always read precomputed MongoDB aggregates so UI response time is independent of underlying data volume.

Final Feasibility Assessment

Why this fits Big Data Analytics
211-million-line, 29.6 GB unstructured corpus with real cross-subsystem schema heterogeneity; structure must be recovered through distributed parsing before any query is meaningful.
Core technical challenge
Mining a consistent, correctly-granular set of log templates from free text at scale, without either over-merging distinct fault types or exploding the template count.
Most difficult implementation component
The PySpark parsing/template-mining stage (Phase 4) — correct, validated masking logic applied consistently across 211 million lines.
Most important viva demonstration
Live proof that parsed events genuinely have heterogeneous fields across templates (two real MongoDB documents with different parameter keys) plus a Spark UI walkthrough of partitions/DAG/shuffle for the parsing job.
Minimum dataset size for a convincing demonstration
The full 29.6 GB Thunderbird log is itself the minimum meaningful unit here — it is not being subsetted, so this question is answered by the dataset's own natural scale.
Minimum viable technical stack
Pseudo-distributed HDFS + PySpark (local mode) + MongoDB + Streamlit + Docker Compose — no multi-node cluster, no FastAPI, no ML classifier required for full rubric coverage.
What should NOT be implemented
A real-time streaming layer (Kafka/Spark Streaming) — the data is a historical batch archive, not a stream; a multi-node physical cluster — unnecessary given pseudo-distributed mode satisfies the Hadoop/PySpark rubric; a deep LSTM anomaly model — GPU is unused by design and adds risk without required marks; do not attempt to reproduce any published paper's accuracy numbers as a target.
